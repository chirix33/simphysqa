# SPQ06 measurement contract confirmation

This describes the frozen implementation at preparation commit `9d245be`, rather than promising fields that it does not save. Main answering has not run. “Recorded” below means actual pilot evidence exists; “future” means the corresponding main procedure is implemented but unexecuted. No metric in this document establishes scientific performance from execution qualification alone.

## Observation and denominator

The scientific unit is a unique QA item and its original trajectory/split group. The final main core contains 200 QA/group identities, ten per domain–family cell. Each receives nine enriched conditions and two prespecified structured-only conditions: 2,200 initial stages and at most 440 conditional stages. Neither conditions, representations, dialogue stages, targets nor alternative rollouts increase the independent sample size. The full prepared pool contains 400 items; the core is nested, not additional.

Primary results retain all selected items for every configured condition/representation. Missing, failed, context-rejected, timed-out, length-limited, invalid and abstained responses contribute zero to positive correctness endpoints. Explanation structured-fact and clarification behavior endpoints remain separate. A failure to execute is an interface/execution failure, not evidence of an incorrect physical belief; nevertheless it is an unsuccessful end-to-end task in the primary denominator. Show both the execution breakdown and fixed-denominator endpoint.

Secondary summaries must name their conditioning set and coverage: completed GPU stages, parseable outputs, typed-valid targets, routed clarifications or completed continuations. They never replace the primary table. The scalar/vector scorer implements valid-only MAE/RMSE with coverage; the main aggregator retains target errors but does not currently generate the scorer’s aggregate channel tables. No new numerical summary or conditional accuracy is silently computed by this confirmation.

## Public/private boundary

All saved main messages contain only the task projection and task response specification; tools=[]; workers import neither SimPhysQA scorers nor simulator routines. Private references, factual/alternative rollouts, answer annotations, authored gold clarification and gold prose remain organizer-only. This package links source/scoring procedures separately; they are not messages sent to answering models.

Explanation tasks deliberately include `input.supplied_comparison` with two selected target outcomes. The exact instruction calls these supplied simulation outcomes, explicitly not observed prefix states. This is task evidence, not private gold prose or an undisclosed future rollout. Clarification initial views keep the accepted full-surface scrub; a supported reply reveals only missing query information and exact public updates. No new cutoff or hidden selector is inserted.

## Required discrepancies before distributing executable work

The existing main runner is a local serial all-condition runner; it has no owner filter, portable executor adapter, immutable import/merge layer or global multi-executor budget enforcement. Frozen workers hard-code RTX5090 and local WSL paths. This confirmation provides unassigned keys and an import contract, **not an implemented distributed executor**. A second GPU is not qualified by these files.

For a later approved implementation, prioritize uniform stop/finish reason; preserved parsed response object plus parser/scorer versions; explicit device-memory source/count/unavailable marker; qualified hardware/runtime receipt on every returned job; total stage latency alongside current generation interval; and immutable central deduplication/budget receipts. Separate prefill/decode measurements and semantic refusal labels are unavailable and must not appear as measured table columns. The frozen workers/prompts/settings were not modified here.

Pinned inherited EOS handling and actual Gemma default/override evidence are confirmed in the catalogue stop-rule addendum. Complete Gemma runtime EOG ID classification is not separately logged. HF/vLLM deadline checks occur at token/engine-step boundaries and can overrun; they are not hard real-time preemption. The main runner also uses a whole-process guard. No settings were changed.
